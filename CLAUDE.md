# expecting

A pregnancy companion for two parents, Australian, on phone and desktop: one shared space that runs the admin, telling you what to do and when (directive about bookings, claims and purchases; never about her body), with a week-by-week "what to expect", the surprising things nobody tells you, and a place to keep what happens. The first version is the pregnancy alone (weeks 1–42); getting ready before it and the weeks after the birth come later. The concept is `docs/intent.md`; what each part does is `docs/product/`.

- **Five pillars:** This week (home, `/`; the strip opens the whole pregnancy at `/timeline`, which is not a pillar), the Library, the Planner (to do, `/planner/weeks`, `/planner/lists`, appointments, questions), the Journal (the story; `/journal/collections`; `/journal/book`) and the Drawer (the names game, Who does what, Your people, bingo).
- **Outside them:** the capture "+" on every pillar (`src/app/features/capture/`), Emergency info (`/emergency`), It's time (`/its-time`, from week 36, 32 for twins), Settings, onboarding (`/onboarding`, a step to a URL).
- **Underneath:** built-in content tailored by the answers (`src/app/features/settings/model/facts.data.ts`) and the extras (`extras.data.ts` beside it), two accounts joined by invite, uploads, the PWA (offline reads and writes), and Claude over MCP (`/api/mcp`, OAuth at `/connect`; `src/api/mcp/`).
- **Not built:** our own entries and hiding built-in ones, contacts as a store, other symptoms, and the phases before and after the pregnancy.

## Constraints

- **Store:** SQLite via `bun:sqlite` is the only store, at `DATA_DIR/expecting.db`. Uploads' bytes are files beside it, in `DATA_DIR/uploads/<id>/` (`original`, and for a picture `display` and `thumb`, made on the phone), each with its `upload` row: `src/server/files/store.ts` keeps and drops them, typed by their first bytes (`sniff`, `src/lib/files.ts`), never SVG or HTML. A record points at its upload (`REFERENCES upload(id)`: `photo.file_id`, `paper_page.file_id`) and deleting the record drops it; one nothing points to is swept a day on. See `docs/architecture.md`, Uploads, and `docs/product/journal.md`. Expecting keeps papers and finds them; it never reads them (no values, no "normal").
- **Queries:** Drizzle ORM (`drizzle-orm/bun-sqlite`) over that same handle. `src/db/models/<domain>/schema.ts` declares a domain's tables, `repo.ts` beside it is its repository. Domains so far: `settings`, `people`, `connections`, `facts`, `appointments`, `extras`, `names`, `emergency`, `checklist`, `questions`, `quiet`, `journal`, `feelings`, `appetite`, `files`, `photos`, `papers`, `firsts`, `lists`, `itsTime`, `circle`, `jobs`, `weekly`, `bingo`, `reads`, `auth`. `src/db/migrations/NNN_name.sql`, applied by `src/db/migrations/migrate.ts`, build the database — drizzle-kit only *generates* SQL to review (`bun run db:generate`), it never applies it.
- **Auth:** two accounts, one each: a `person` row is one of you (two at most, one in each role, held by a trigger), with your own password's argon2id hash. No usernames: `/login` shows your names, then asks your password; on a new instance it sets it up as whichever of you comes first (`setUp`), and the other joins only by an invite from Settings (`/join?code=…`). A 400-day session cookie whose token is stored only as a SHA-256 says whose it is (`session.person_id`), and is the only way the server knows who you are (`personId()`, `sessionOf`). Invites and resets are codes, only their SHA-256 kept (`invite`; `InviteRepo`). `src/server/auth/gate.ts` holds the rule, applied twice in `src/start.ts`: request middleware judges pages and `/api/*` by path (only `/login`, `/join`, `/reset`, `/api/health` and the OAuth endpoints are open; `/api/mcp` goes on to its handler, judged by its bearer token, `grantOf`), and function middleware judges every server function by the file it is defined in (only `src/api/rpc/session.ts`, which holds `getAccess`, `setUp`, `login`, `checkCode`, `join`, `resetPassword` and `logout`, is open). Nothing else goes in that file. Each of you can make the other a reset link; alone, turn logins off, choose a new password in Settings, and turn them back on. `EXPECTING_LOGIN=off` (default `on`) stops asking for passwords, not who you are: the gate is the same, and logging in is tapping your name.
- **Timeline:** `src/lib/timeline.ts` is the spine. A `Week` is a pregnancy week, 1–42 (completed weeks of gestation), and is its own URL key: `/timeline?at=28`. The current week is derived from the due date on read, never stored.
- **Content:** built-in items are `content/items/<id>.md` (the name is the id), frontmatter validated by `src/content/schema.ts`, bundled into the client by `src/content/index.ts`. A bad file fails `bun run test` (`test/content/`). Ids are stable slugs: ticks point at them, so never rename one. Each is one of eight `type`s (`moment`, `payment`, `decision`, `can-i`, `symptom`, `guide`, `card`, `term`), each with its body's shape, and has one `topic` (`TOPICS`); weeks are optional. How to write one is `content/README.md`; how it's reviewed, and the calls made, `content/REVIEW.md`. A task may give `opens`, `due` (best by), a `deadline` (only from the item's source) and `who` (`carrying`, `partner`, `together`). An item may give `lines`, what to get, each on one of `LISTS` (`src/lib/planner/lists/builtIn.ts`) in one of its sections, with its own `when` and its item's `task`; ids stable like tasks'. A decision's `decide_by` (only from its source, within its weeks) makes it a task, `decide-<id>`. An item may belong to an extra (`extra: baby-shower`, from `src/app/features/settings/model/extras.data.ts`): shown only while it's on. `private: true` (family violence, reproductive coercion) leaves no trace in the shared space: no tasks, `decide_by`, `when`, extra or `{% ask %}`; never offered unasked; every link to an entry is `ItemLink` (`src/pillars/library/components/itemLink/ItemLink.tsx`), which masks a private one's address; its page has a quick exit; and `src/server/privacy/` refuses any server function's input that names one (`test/server/private.test.ts` lists every write path). See `docs/architecture.md`, Content. Each week's note is `content/weeks/<week>.md`, named for the week (`28`), with three `##` parts, The baby, Your body and For the partner, checked by `src/content/weeks.ts`. Each day after it, +1 to +6, has a read, `content/days/<week>/<day>.md`, a short way into the Library from where you are (`read:` names its entries, which hold every claim it makes), checked by `src/content/days.ts`, shown on This week one a day in a carousel. The questions (`src/app/features/settings/model/facts.data.ts`) and the extras (`src/app/features/settings/model/extras.data.ts`) drive behaviour, so they are typed lists co-located with settings, beside their rules (`facts.ts`, `extras.ts`), not in `content/`, which is only the writing. They are pure: `lib/` and `content/` may import them and nothing else in `features/`. Never add a draft marker: an entry ships only once it is written and reviewed (`content/REVIEW.md`); `checked:` only when its facts were confirmed against its source.
- **Framework:** TanStack Start (React 19). Routing is code, not file names. Each pillar and feature with addresses has a `routes/` folder of definitions only: a file per route, named for its own path within it, and an `index.ts` that puts its subtree together. The Journal's: `journal.ts` (`path: "journal"`, a path and nothing else, so nothing wraps its pages and each draws its own `PillarLayout`), `story.ts` (its index, `/journal`), `collections.ts` (a path, with the loader all its children share) over `collectionsIndex.ts` and `collection.ts` (`$name`), `book.ts`, and `index.ts`, `journalRoutes`. A feature's subtree is added by its pillar's (`plannerRoutes` adds `listsRoutes` and `weeks`, `src/pillars/planner/features/{lists,weeks}/routes/`); one route alone needs no `index.ts`. A loader on a path-only route only when every child reads it; the rest stay on their leaves. Each search schema is in the route that owns it, its `validateSearch` on that leaf. `src/routes/` keeps only `root.tsx` (the root route), `app.tsx` (the pathless route `App` draws in `AppLayout`), `notFound.ts` and `tree.ts` (the tree's shape, and nothing else: the subtrees, in navigation order). A new route is a new file in its feature's `routes/`, added to its subtree. A route whose page is different while something has happened names each world's page with `worlds(normal, quiet)` (`src/app/features/quiet/worlds.tsx`), both lazy, or `putAway({…})` (`putAway.tsx` beside it) for a page put away. Everything that answers at `/api` lives in `src/api/`: `rest/` the server routes (`/api/health`, `/api/files/<id>/<variant>`), which `tree.ts` adds to the tree on the server only, and `rpc/` the server functions, served under `/api/rpc/`, each file with its query and hooks beside them (`serverFns.base` in `vite.config.ts`). Pages live in `src/pillars/` and `src/app/features/` and read their route by its id with `getRouteApi("/app/library/")` (an index's id ends in `/`); nothing imports a `routes/` folder but other routes and `tree.ts`. No `createFileRoute`. Vite is its build tool, run via `bun --bun vite`. This overrides the generic Bun guidance below about HTML imports and avoiding Vite. Server functions (in `src/api/rpc/`, the only way the browser reaches `src/server/` and the store) for the app's own data calls; server routes (`src/api/rest/`) only for endpoints outside callers need (health, `/api/mcp` and the OAuth endpoints), and two deliberate exceptions, behind the gate like every `/api/*` path: an upload's bytes (`/api/files/<id>/<variant>`, `src/api/rest/files.ts`), which an `<img>` fetches by a plain URL, and an appointment's calendar file (`/api/appointments/<id>/calendar.ics`, `src/api/rest/calendar.ts`), which a phone hands to its calendar only from a plain URL. Uploads go up through a server function (`putUpload`, `src/api/rpc/files.ts`), as a form.
- **Rendering:** SPA mode (`spa.enabled`), in production as in dev: every page request gets the shell (`src/server/shellMode.ts` sets `TSS_SHELL`, imported first in `src/server.ts`). Don't give a route `ssr`.
- **Frontend:** React 19 + Tailwind 4 via `@tailwindcss/vite`. One app, the pregnancy: its pillars are `PILLARS` (`src/app/components/layout/pillars.ts`), drawn by `App` in `AppLayout`, each at its own path, every page in a pillar drawing `PillarLayout` (its column and top) (`/`, `/library`, `/planner`, `/journal`, `/drawer`). There are no phases in the code for now: no phase type, no phase in the URL, no birth date (`docs/architecture.md`, One app, the pregnancy). Pages and their parts live in `src/pillars/<pillar>/` (`thisWeek`, `library`, `planner`, `journal`, `drawer`): a pillar's own page at its top, and what lives in it, with its own store or pages, a feature under it, `src/pillars/<pillar>/features/<feature>/` (`planner/features/tasks`, `drawer/features/names`, `journal/features/photos`, …). What's outside the pillars is `src/app/features/<feature>/` (`capture`, `emergency`, `itsTime`, `quiet`, `settings`, `onboarding`, `auth`, `connect`), beside the app itself (the document, the app's layout `AppLayout`, the error pages, `useAction`), `src/app/`. A pillar and every feature have one shape, each folder only where it has something: `pages/`, `components/<aspect>/` (shared parts loose in `components/`), `hooks/`, `contexts/` (a page's context, one at most), `model/` (no React: rules, types, paths), `routes/` (its addresses, definitions only) and, for a pillar, `features/`; each pillar has a `README.md`, the map of its code. Settings' `model/` (`src/app/features/settings/model/`) is the only part of them that `lib/` and `content/` may import (see `docs/architecture.md`, Code layout); `src/components/` only for generic parts with no domain. Biome's `noRestrictedImports` holds the layers (see `docs/architecture.md`, Code layout). Each thing lives in one pillar; anything with a date also appears on its week (This week, the whole pregnancy at `/timeline`, `src/pillars/thisWeek/features/timeline/`), the thread between them. New features go into a pillar, not a new top-level page. Quiet (something has happened) is a mirror world of each pillar: what's different while quiet is the pillar's or feature's `quiet/` (`pages/`, `contexts/` only where needed, `components/`), its rules `src/lib/<pillar>/quiet.ts`; the route's file is the one place that chooses, through `worlds()`, each world's page in its own provider; no page and no layout checks quiet to choose, and the address is the same in both (`docs/architecture.md`, Something has happened). The query cache is the only store of data, a query per thing; no data provider and no aggregate. A page may have one context, its organising layer: `<Page>Provider` and `use<Page>Page()` in its pillar's or feature's `contexts/<Page>PageContext.tsx` (only where a page has one), holding its state (search words, …), what must be worked out once and what several parts must agree on, while what only one part needs that part works out itself; reading queries through their hooks and never keeping a copy; its parts read it rather than take it as props (`JournalPageProvider`, `src/pillars/journal/contexts/JournalPageContext.tsx`, and the Planner's, Settings', This week's, …). Each `src/api/rpc/<thing>.ts` holds both sides of its thing: the server functions, the query (`answersQuery`, …) and its hook, `use<Thing>Query` (`useAnswersQuery`, …; `usePosition` and `useNow`, worked out from settings rather than a query, keep their names): `useSuspenseQuery` over the query, returned as is, with any options (`select`, …) overriding its defaults. So `const { data: facts } = useAnswersQuery({ select: factsOf })`. Settings also has `usePosition` and `useNow`. `useItems` (the Library) and `useTasks` (the Planner's tasks) combine several. See `docs/architecture.md`. Adaptive: two experiences, a mobile one (a phone) and a desktop one (`lg` and up), each still responsive within itself. `useLayout()` (`src/app/hooks/useLayout.ts`, `"mobile" | "desktop"`) chooses where the structure differs, never drawing both and hiding one; the `desktop:` and `mobile:` variants (from `<html data-layout>`, set on the same line) for the same structure spaced or sized differently; no `lg:` (a test keeps it out); what's only one's is in `mobile/` or `desktop/` beside what it splits (the one shape, like `quiet/`; the app's own `MobileLayout` and `DesktopLayout`, chosen by `AppLayout`), what both draw outside both, and Biome keeps the two from importing each other. A page chooses under its provider; the address is the same. On a desktop, what you look at opens in the side panel beside the page (`src/app/desktop/components/panel/`): an entry by every `ItemLink` (`?panel=item:<id>`), and anything opened from a list to look at and change through `DetailSheet` (`src/app/components/DetailSheet.tsx`, a sheet on a phone); something to do and be done with stays a `Modal`. See `docs/architecture.md`, Adaptive and The app's layout.
- **UI kit:** `@sixthshift/design-system` (Jason's personal system), from the npm registry. Subpath imports only, e.g. `@sixthshift/design-system/button`. Check its exports before writing any UI element. The theme is Expecting's own, not Linen: `src/styles/theme/` (palette generated by `bun run palette`, never edited by hand; three themes, Baby Blue, Baby Pink and Baby Purple, switched by `data-expecting-theme`, each light or dark per phone by the design system's `data-theme`). Components use semantic tokens only, never palette colours.
- **Locale:** metric, en-AU spelling. UUID ids, zod validation.
- **Tests:** vitest via `bun run test`. Not `bun test`. Two projects in one command: everything runs in `node`, except `*.dom.test.tsx`, which gets happy-dom and Testing Library. `bun run e2e` is Playwright over the production build, specs in `e2e/` importing `e2e/fixtures.ts` (not `@playwright/test`). The gate is `check`, `test`, `lint` and `e2e`.
- **Port:** 9966 everywhere — dev, `bun run start` and the image. e2e serves on 9967 (a worktree on its own port, from its path).
- **PWA:** `public/manifest.webmanifest` and the icons are public files, served ahead of the gate. The service worker is hand-written (`src/pwa/worker.js`, no Workbox) and emitted as `/sw.js` by `src/pwa/vite.ts` in a build only, with the build's files written in; dev has none. Queries are `networkMode: "offlineFirst"` so the worker can answer offline. Every save goes through the outbox (`src/app/model/outbox.ts`): a `Save` beside its server function, listed in `src/app/model/saves.ts`, made with `useSave`; its `apply` must give the same answer run twice. A save with an upload keeps its parts on the phone first (`keepOnPhone`, IndexedDB, `src/app/model/uploads.ts`) and sends them in its `send` (`withUpload`, `withUploads` for a paper's pages), so a photo taken offline waits and goes up later. The worker keeps uploads' thumbnails and display copies (`expecting-files`, cache first), and originals only for a handy paper, which the page puts there itself (`keepHandyOffline`). Sharing in from another app: the manifest's `share_target` posts to `/share`, which only the worker answers, keeping it (`expecting-shared`) for the app's layout to take into the "+" (`src/pwa/share.ts`, `SharedIn`); Android only, Safari has no share target.
- **Parallel sessions:** several sessions may work at once. A stream of work in a worktree is `.claude/worktrees/<name>` on branch `feat/<name>`; `bun install` there first. The dev server's 9966 is strictPort, so in a worktree pass `--port`; e2e already takes its own port, and waits its turn behind other worktrees' runs (a machine-wide lock), so run it in the background. `main`'s tree may hold another session's uncommitted work: commit only your own files, and run the gate on a clean tree (a throwaway worktree at your commit) when it's dirty.
- **Deploy:** one Docker container, SQLite file on a volume.

## Conventions

Default to using Bun instead of Node.js.

- Use `bun <file>` instead of `node <file>` or `ts-node <file>`
- Tests use vitest, run as `bun run test`. Never `bun test`. This overrides the generic Bun guidance.
- Use `bun install` instead of `npm install` or `yarn install` or `pnpm install`
- Use `bun run <script>` instead of `npm run <script>` or `yarn run <script>` or `pnpm run <script>`
- Use `bunx <package> <command>` instead of `npx <package> <command>`
- Bun automatically loads .env, so don't use dotenv.

## APIs

- HTTP is handled by TanStack Start's server (Nitro, Bun preset). Don't add `express` or a second server.
- `bun:sqlite` for SQLite, with Drizzle as the query builder over it. Don't use `better-sqlite3`.
- `WebSocket` is built-in. Don't use `ws`.
- Prefer `Bun.file` over `node:fs`'s readFile/writeFile
- Bun.$`ls` instead of execa.

## Frontend

This project uses TanStack Start, not Bun HTML imports. Vite is run through Bun:

```json
{ "dev": "bun --bun vite dev --host", "build": "bun --bun vite build", "start": "bun run .output/server/index.mjs" }
```

`vite.config.ts` plugins: `tanstackStart({ spa: { enabled: true } })`, `nitro({ preset: "bun" })`, `viteReact()`, `tailwindcss()`. Server functions via `createServerFn`, validated with zod. `bun:sqlite` is imported only from server code.

For more information, read the Bun API docs in `node_modules/bun-types/docs/**.mdx`.
