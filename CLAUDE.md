# expecting

A personal pregnancy companion (later perhaps newborn and parenting) for two parents that runs the admin, telling you what to do and when (directive about bookings, claims and purchases; never about her body): a shared checklist, a week-by-week "what to expect", the surprising things people don't know, and a shared store for information. One shared space for both parents, on phone and desktop, Australian. The concept is in `docs/intent.md`. The first version is the pregnancy alone (getting ready before it and the weeks after the birth come later), and the app is six pillars: This week (home: where you are, the week's note, what to do), the Timeline (the map: every week a line, and what each item asks of you drawn across its weeks), the Library (everything Expecting knows), the Planner (to do, the lists of what to get at `/planner/lists`, and questions: `docs/product/planner.md`), the Journal (one story of everything kept and done, newest first under its week, with what matters now first, the patterns there's enough for, a lens a kind and a zoom out: notes and letters, movements, sickness and cravings, photos and scans, how you're feeling, results and papers, and the firsts; recaps and a book at `/journal/book`; it shows what's kept, never what's missing: `docs/product/journal.md`) and the Drawer (the handy things: the names game and Your people, each with its extras; the rest placeholders), plus the capture "+" on every pillar (`src/features/capture/`: a movement, sickness, a craving, a note, a photo or scan, a result or paper, a feeling, a first, a question or a task, each filed into its pillar; the Journal's Keep row is its Journal choices), plus Emergency info (its own page beside settings, at `/emergency`, with the papers kept handy), plus It's time (the page for the night it starts, at `/its-time`, beside Emergency info from week 36, 32 for twins: the calls, the contraction timer, the waters, what they'll ask, the bag and its last things, getting there; `docs/product/its-time.md`), plus built-in content (Markdoc, tailored by the answers in `src/features/settings/model/facts.data.ts`, asked up front and again on This week as they come due, and by the extras in `src/features/settings/model/extras.data.ts`, off until turned on), onboarding at `/onboarding`, a step to a URL, who's holding each phone, own tasks, the shared password, uploads (the file store, for any record), and the PWA (install, offline reads through a service worker, and offline writes through an outbox). The rest of the store is not.

## Constraints

- **Store:** SQLite via `bun:sqlite` is the only store, at `DATA_DIR/expecting.db`. Uploads' bytes are files beside it, in `DATA_DIR/uploads/<id>/` (`original`, and for a picture `display` and `thumb`, made on the phone), each with its `upload` row: `src/server/files/store.ts` keeps and drops them, typed by their first bytes (`sniff`, `src/lib/files.ts`), never SVG or HTML. A record points at its upload (`REFERENCES upload(id)`: `photo.file_id`, `paper_page.file_id`) and deleting the record drops it; one nothing points to is swept a day on. See `docs/architecture.md`, Uploads, and `docs/product/journal.md`. Expecting keeps papers and finds them; it never reads them (no values, no "normal").
- **Queries:** Drizzle ORM (`drizzle-orm/bun-sqlite`) over that same handle. `src/db/models/<domain>/schema.ts` declares a domain's tables, `repo.ts` beside it is its repository. Domains so far: `settings`, `people`, `facts`, `extras`, `names`, `emergency`, `checklist`, `questions`, `quiet`, `journal`, `feelings`, `appetite`, `files`, `photos`, `papers`, `firsts`, `lists`, `itsTime`, `circle`, `jobs`, `weekly`, `auth`. `src/db/migrations/NNN_name.sql`, applied by `src/db/migrations/migrate.ts`, build the database — drizzle-kit only *generates* SQL to review (`bun run db:generate`), it never applies it.
- **Auth:** one shared password, chosen on the first visit (`/login` asks for it while none is set), its argon2id hash stored in the database (`password`, one row; `PasswordRepo`), and a 400-day session cookie whose token is stored only as a SHA-256. No users, no accounts. `src/server/auth/gate.ts` holds the rule, applied twice in `src/start.ts`: request middleware judges pages and `/api/*` by path (only `/login` and `/api/health` are open), and function middleware judges every server function by the file it is defined in (only `src/api/rpc/session.ts`, which holds `choosePassword`, `login` and `logout`, is open). Nothing else goes in that file. No reset in the app: a new database is the reset. `EXPECTING_LOGIN=off` (default `on`) turns logins off: the gate lets everything through; who's holding the phone is still asked.
- **Timeline:** `src/lib/timeline.ts` is the spine. A `Week` is a pregnancy week, 1–42 (completed weeks of gestation), and is its own URL key: `/timeline?at=28`. The current week is derived from the due date on read, never stored.
- **Content:** built-in items are `content/items/<id>.md` (the name is the id), frontmatter validated by `src/content/schema.ts`, bundled into the client by `src/content/index.ts`. A bad file fails `bun run test` (`test/content/`). Ids are stable slugs: ticks point at them, so never rename one. Each is one of eight `type`s (`moment`, `payment`, `decision`, `can-i`, `symptom`, `guide`, `card`, `term`), each with its body's shape, and has one `topic` (`TOPICS`); weeks are optional. How to write one is `content/README.md`; the review pass's calls are `content/REVIEW.md`. A task may give `opens`, `due` (best by), a `deadline` (only from the item's source) and `who` (`carrying`, `partner`, `together`). An item may give `lines`, what to get, each on one of `LISTS` (`src/lib/lists.ts`) in one of its sections, with its own `when` and its item's `task`; ids stable like tasks'. A decision's `decide_by` (only from its source, within its weeks) makes it a task, `decide-<id>`. An item may belong to an extra (`extra: baby-shower`, from `src/features/settings/model/extras.data.ts`): shown only while it's on. `private: true` (family violence, reproductive coercion) leaves no trace in the shared space: no tasks, `decide_by`, `when`, extra or `{% ask %}`; never offered unasked; every link to an entry is `ItemLink` (`src/features/library/components/ItemLink.tsx`), which masks a private one's address; its page has a quick exit; and `src/server/privacy/` refuses any server function's input that names one (`test/server/private.test.ts` lists every write path). See `docs/architecture.md`, Content. Each week's note is `content/weeks/<week>.md`, named for the week (`28`), with three `##` parts, The baby, Your body and For the partner, checked by `src/content/weeks.ts`. The questions (`src/features/settings/model/facts.data.ts`) and the extras (`src/features/settings/model/extras.data.ts`) drive behaviour, so they are typed lists co-located with settings, beside their rules (`facts.ts`, `extras.ts`), not in `content/`, which is only the writing. They are pure: `lib/` and `content/` may import them and nothing else in `features/`. There is no draft marker: an entry ships once it is written and reviewed; `checked:` only when its facts were confirmed against its source.
- **Framework:** TanStack Start (React 19). Routing is code, not file names: `src/routes/` holds definitions only — `root.tsx` (the root route), a file per route (`app.tsx`, the pathless frame drawn by `App`; `index.ts` for `/`, This week; `timeline.ts`, `library.ts`, `libraryItem.ts`, `planner.ts`, `journal.ts`, `drawer.ts`, `emergency.ts` for `/emergency`, `itsTime.ts` for `/its-time`, `settings.ts`), `onboarding/` (its layout route, `next.ts` for `/onboarding`, then a file per step), `auth/` (`login.ts`, at `/login`: the folder only groups it), `tree.ts` (the tree's shape, and nothing else) and `search.ts` (search schemas). A new route is a new file, added to `tree.ts`. Everything that answers at `/api` lives in `src/api/`: `rest/` the server routes (`/api/health`, `/api/files/<id>/<variant>`), which `tree.ts` adds to the tree on the server only, and `rpc/` the server functions, served under `/api/rpc/`, each file with its query and hooks beside them (`serverFns.base` in `vite.config.ts`). Pages live in `src/features/` and read their route with `getRouteApi("/app/library")`; nothing imports from `routes/`. No `createFileRoute`. Vite is its build tool, run via `bun --bun vite`. This overrides the generic Bun guidance below about HTML imports and avoiding Vite. Server functions (in `src/api/rpc/`, the only way the browser reaches `src/server/` and the store) for the app's own data calls; server routes (`src/api/rest/`) only for endpoints outside callers need (health), and one deliberate exception: an upload's bytes (`/api/files/<id>/<variant>`, `src/api/rest/files.ts`), which an `<img>` fetches by a plain URL, behind the gate like every `/api/*` path. Uploads go up through a server function (`putUpload`, `src/api/rpc/files.ts`), as a form.
- **Rendering:** SPA mode (`spa.enabled`), in production as in dev: every page request gets the shell (`src/server/shellMode.ts` sets `TSS_SHELL`, imported first in `src/server.ts`). Don't give a route `ssr`.
- **Frontend:** React 19 + Tailwind 4 via `@tailwindcss/vite`. One app, the pregnancy: its pillars are `PILLARS` (`src/app/components/layout/pillars.ts`), drawn by `App` in `PillarLayout`, each at its own path (`/`, `/timeline`, `/library`, `/planner`, `/journal`, `/drawer`). There are no phases in the code for now: no phase type, no phase in the URL, no birth date (`docs/architecture.md`, One app, the pregnancy). Pages and their parts live by domain in `src/features/<domain>/`; the app itself (the document, the frame, the error pages, `useAction`) is `src/app/`, outside the features, in the same shape; every feature has one shape, each folder only where it has something: `pages/`, `components/<aspect>/` (shared parts loose in `components/`), `hooks/` and `model/` (no React: rules, types, paths). Settings' `model/` is the only part of `features/` that `lib/` and `content/` may import (see `docs/architecture.md`, Code layout) (`thisWeek`, `timeline`, `library`, `planner`, `journal`, `drawer`, `emergency`, …); `src/components/` only for generic parts with no domain. Biome's `noRestrictedImports` holds the layers (see `docs/architecture.md`, Code layout). Each thing lives in one pillar; anything with a date also appears on its week in the timeline (`src/features/timeline/`), the thread between them. New features go into a pillar, not a new top-level page. The query cache is the only state, a query per thing; no provider and no aggregate. Each `src/api/rpc/<thing>.ts` holds both sides of its thing: the server functions, the query (`answersQuery`, …) and its hook (`useAnswers`, …): `useSuspenseQuery` over the query, returned as is, with any options (`select`, …) overriding its defaults. So `const { data: facts } = useAnswers({ select: factsOf })`. Settings also has `usePosition` and `useNow`. `useItems` (library) and `useTasks` (tasks) combine several. See `docs/architecture.md`. Adaptive: a layout designed for a phone and one designed for desktop (`lg` and up). See `docs/architecture.md`.
- **UI kit:** `@sixthshift/design-system` (Jason's personal system), from the npm registry. Subpath imports only, e.g. `@sixthshift/design-system/button`. Check its exports before writing any UI element. The theme is Expecting's own, not Linen: `src/styles/theme/` (palette generated by `bun run palette`, never edited by hand; three themes, Baby Blue, Baby Pink and Baby Purple, switched by `data-expecting-theme`, each light or dark per phone by the design system's `data-theme`). Components use semantic tokens only, never palette colours.
- **Locale:** metric, en-AU spelling. UUID ids, zod validation.
- **Tests:** vitest via `bun run test`. Not `bun test`. Two projects in one command: everything runs in `node`, except `*.dom.test.tsx`, which gets happy-dom and Testing Library. `bun run e2e` is Playwright over the production build, specs in `e2e/` importing `e2e/fixtures.ts` (not `@playwright/test`). The gate is `check`, `test`, `lint` and `e2e`.
- **Port:** 9966 everywhere — dev, `bun run start` and the image. e2e serves on 9967 (a worktree on its own port, from its path).
- **PWA:** `public/manifest.webmanifest` and the icons are public files, served ahead of the gate. The service worker is hand-written (`src/pwa/worker.js`, no Workbox) and emitted as `/sw.js` by `src/pwa/vite.ts` in a build only, with the build's files written in; dev has none. Queries are `networkMode: "offlineFirst"` so the worker can answer offline. Every save goes through the outbox (`src/app/model/outbox.ts`): a `Save` beside its server function, listed in `src/app/model/saves.ts`, made with `useSave`; its `apply` must give the same answer run twice. A save with an upload keeps its parts on the phone first (`keepOnPhone`, IndexedDB, `src/app/model/uploads.ts`) and sends them in its `send` (`withUpload`, `withUploads` for a paper's pages), so a photo taken offline waits and goes up later. The worker keeps uploads' thumbnails and display copies (`expecting-files`, cache first), and originals only for a handy paper, which the page puts there itself (`keepHandyOffline`). Sharing in from another app: the manifest's `share_target` posts to `/share`, which only the worker answers, keeping it (`expecting-shared`) for the frame to take into the "+" (`src/pwa/share.ts`, `SharedIn`); Android only, Safari has no share target.
- **Parallel sessions:** several sessions work at once, coordinated by one coordinator session (`workspace-58`). Every stream of work gets a worktree, `.claude/worktrees/<name>` on branch `feat/<name>`; `bun install` there first. In a worktree, commit on your branch only: never merge, rebase or push `main` yourself. The dev server's 9966 is strictPort, so in a worktree pass `--port`; e2e already takes its own port, and waits its turn behind other worktrees' runs (a machine-wide lock), so run it in the background. When the work is done and the gate passes, ask to land it: `echo "<your session name (ListAgents shows it)>: <one line: what it is, gate result>" > "$(git rev-parse --git-common-dir)/coord/ready/<name>"` (or message `workspace-58`), then leave the worktree clean. The coordinator rebases it onto `main`, runs the gate, fast-forwards `main` and tells you; on a conflict it hands the rebase back to you. Every stream works in a worktree, never in `/workspace` on `main`; only the coordinator changes `main`.
- **Deploy:** one Docker container, SQLite file on a volume.

## Conventions

Default to using Bun instead of Node.js.

- Use `bun <file>` instead of `node <file>` or `ts-node <file>`
- Tests use vitest, run as `bun run test`. Never `bun test`. This overrides the generic Bun guidance.
- Use `bun install` instead of `npm install` or `yarn install` or `pnpm install`
- Use `bun run <script>` instead of `npm run <script>` or `yarn run <script>` or `pnpm run <script>`
- Use `bunx <package> <command>` instead of `npx <package> <command>`
- Bun automatically loads .env, so don't use dotenv.

## APIs

- HTTP is handled by TanStack Start's server (Nitro, Bun preset). Don't add `express` or a second server.
- `bun:sqlite` for SQLite, with Drizzle as the query builder over it. Don't use `better-sqlite3`.
- `WebSocket` is built-in. Don't use `ws`.
- Prefer `Bun.file` over `node:fs`'s readFile/writeFile
- Bun.$`ls` instead of execa.

## Frontend

This project uses TanStack Start, not Bun HTML imports. Vite is run through Bun:

```json
{ "dev": "bun --bun vite dev --host", "build": "bun --bun vite build", "start": "bun run .output/server/index.mjs" }
```

`vite.config.ts` plugins: `tanstackStart({ spa: { enabled: true } })`, `nitro({ preset: "bun" })`, `viteReact()`, `tailwindcss()`. Server functions via `createServerFn`, validated with zod. `bun:sqlite` is imported only from server code.

For more information, read the Bun API docs in `node_modules/bun-types/docs/**.mdx`.
